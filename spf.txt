Symbolic PathFinder in this project: the problems we hit and how we got past them
==================================================================================

TestGen asks Symbolic PathFinder (SPF, jpf-symbc on top of jpf-core) for one
thing: values for the inputs of the next call of a test string. Each
section below is one problem we met along the way. It says what went wrong,
why SPF behaves that way, what we did about it, and where the fix lives.
Paths are relative to pl-platform-testing/src/main/java/in/ac/iiitb/plproject/
unless they start at the repository root.


1. jpf-core and jpf-symbc are not on Maven Central
--------------------------------------------------
Problem: Neither project publishes jars to Maven Central, so the Maven build
cannot simply depend on them.

Why: JPF and SPF are distributed only as source on GitHub, and they are built
with Gradle (jpf-core) and Ant (jpf-symbc).

Fix: scripts/setup-spf.sh (repository root) clones both projects at pinned
commits, builds them, and installs the jars into the local Maven repository
under fixed coordinates:
  - jpf-core  commit f70927ce05b165addb02e9c232af74e9737e09bf (master,
    2025-12-16), built with ./gradlew buildJars, installed as
    gov.nasa.jpf:jpf-core:8.0-f70927c
  - jpf-symbc commit 3bedf0b168b3c85dd0f05434dd61c4c011cc447a (master,
    2022-06-08), built with ant build, installed as
    gov.nasa.jpf:jpf-symbc:1.0-3bedf0b
  - Java 11 is needed for both projects and for this project. jpf-symbc's
    prebuilt class files are version 52, and they break when read by a JDK 8
    javac sitting behind a JDK 11 build of jpf-core. So we use JDK 11
    (java-11-openjdk-amd64) everywhere.
jpf-symbc's build.xml looks for jpf-core through ~/.jpf/site.properties, or
otherwise in a ../jpf-core folder next to it. The script writes that file
explicitly, so it does not depend on (or clobber) any other JPF install. The
checkouts live in ~/.genatc-spf (override with --spf-home or
GENATC_SPF_HOME). The jars are "provided" dependencies in
pl-platform-testing/pom.xml, so generated JUnit classes never depend on them.
Where: scripts/setup-spf.sh; spf/SpfHome.java (finds the checkouts and
RunJPF.jar).


2. Two jar families with different classes
------------------------------------------
Problem: Code compiled against the "JPF jar" failed in confusing ways: either
Verify/Debug were missing, or Config/JPF/PathCondition were.

Why: Each project builds two jars, and they hold different classes.
jpf-classes.jar and jpf-symbc-classes.jar hold the small set of classes the
program under test sees (Verify, Debug). jpf.jar and jpf-symbc.jar are the
engine itself (Config, JPF, Search, PathCondition, listeners).

Fix: The generator's own listeners are compiled against the engine jars (the
Maven dependency). The generated SPF driver is compiled against the
target-side jars, which are taken straight from the checkout and never come
through Maven.
Where: spf/SpfHome.java (resolveDriverCompileClasspath), spf/SpfSymexEngine.java
(compile, writeJpfConfig), scripts/setup-spf.sh.


3. The native_classpath delimiter
---------------------------------
Problem: SPF reported "class not found ...PathVectorListener" even though the
listener was on the classpath we gave it.

Why: JPF's Config splits classpath and native_classpath on commas, not on the
platform path separator (':' on Linux). The colon-joined lists we wrote were
read as one long, invalid path.

Fix: Every entry of classpath and native_classpath in the generated run.jpf
is joined with ','. This was confirmed by reading Config.java and by
experiment.
Where: spf/SpfSymexEngine.java, writeJpfConfig (commit b6bbb20).


4. Keeping JPF out of the generator's JVM
-----------------------------------------
Problem: Referring to the listener classes from generator code would load
gov.nasa.jpf.* into the generator JVM, where those classes are not present.
A stuck SPF search could also hang the generator.

Why: The JPF engine is only a "provided" dependency, and an SPF search can
run for a long time.

Fix: SPF runs as a separate process (java -jar RunJPF.jar run.jpf) for each
genCTC round. The listeners are named only as strings in run.jpf, and their
classes come from native_classpath. The process is killed if it runs longer
than the SPF time limit plus 30 seconds.
Where: spf/SpfSymexEngine.java (runDriver, runSpfProcess, writeJpfConfig).


5. Debug.assume does not prune a concrete boolean
-------------------------------------------------
Problem: Preconditions written as Debug.assume(cond) pruned nothing, so
impossible paths went through.

Why: In jpf-symbc 3bedf0b, Debug.assume only prunes when its argument still
carries a symbolic attribute. Java has already turned a comparison into a
branch that yields a plain true/false, so by the time Debug.assume sees the
value it is concrete and is ignored.

Fix: Every assume is printed as
  try { ok = (cond); } catch (RuntimeException e) { ok = false; } Verify.ignoreIf(!ok);
SPF branches when it evaluates cond. Verify.ignoreIf then drops the branch
where the condition is false.
Where: symbolic/SymbolicDriverPrinter.java (printStatement).


6. Integer.valueOf branches on the integer cache
------------------------------------------------
Problem: Boxing a symbolic int with Integer.valueOf (or autoboxing) split the
search into extra paths, and those paths had nothing to do with the contract.

Why: Integer.valueOf checks whether the value is in the cache range -128..127.
On a symbolic value, that check is a branch SPF has to explore.

Fix: Boxed symbolic inputs are created as
new Integer(Debug.makeSymbolicInteger("x")), which does not branch.
Where: symbolic/SymbolicDriverPrinter.java (symbolicInput).


7. Division and remainder by a symbolic value (IDIV/IREM)
---------------------------------------------------------
Problem: Any '/' or '%' whose divisor was symbolic threw
"ArithmeticException: div by 0", even when the path condition said the
divisor was positive. MathLib.gcd could not be run at all, and the old
pipeline reported it as EXECUTION_ERROR.

Why: jpf-symbc's IDIV/IREM handlers first check whether the divisor is zero,
using its concrete shadow value. For a fresh symbolic int that value is the
JVM default, 0. The check fires before the path condition is ever consulted.
We reproduced this with a six-line program, with both z3 and choco.

Fix: The TestGen design avoids the problem. A library call runs only when all
its arguments are concrete (isReady), so gcd's own '%' always runs on
concrete numbers. The contract's "a % divisor == 0" is a postcondition, and
postconditions are checked only in the final JUnit test, on concrete values.
mathlib now generates, and its test passes. The jpf-symbc bug is still there:
a precondition that divides by a symbolic input would still hit it.
Where: symbolic/TestGen.java (isReady, symex); the analysis is in
IMPLEMENTATION_NOTES.md and commit b6bbb20.


8. Error states were reported as solved paths
---------------------------------------------
Problem: When a path ended in an uncaught exception, the listener still
solved its path condition and reported it as a usable test. This also hid the
IREM problem behind "infeasible precondition".

Why: To SPF, an end state is an end state, whether the program completed or
the search stopped on a property violation.

Fix: The listener checks Search.getCurrentError(). An error end state is
written as its own "error" event, together with the driver line that was
running. It is never a path. The engine reports a ready call that throws on
every path as LIBRARY_EXCEPTION and names the call.
Where: spf/listener/PathVectorListener.java (stateAdvanced, instructionExecuted);
spf/SpfSymexEngine.java (interpret). First fixed in commit b6bbb20.


9. Symbolic strings and hashing are not solvable
------------------------------------------------
Problem: When a symbolic String, or a symbolic int used as a Set/Map key,
reached java.util.HashMap or HashSet, the solver failed: "Error Z3", or
"Choco does not support bitwise SHIFT". jpf-symbc's string solver is a
separate, fragile setup that this project does not enable.

Why: HashMap.hash() spreads hashCode() bits with shifts and XORs. With a
symbolic key, those bit operations go into the path condition, and neither
solver accepts them. String.hashCode/equals on a symbolic string needs a
string solver.

First fix (now removed): a literal pool. Every String, and every number the
contract used as a key, was chosen from three fixed values ("s1","s2","s3" /
101,103,105) plus the members of the real collection, using a symbolic
index. The driver had a pick() helper, and a static "picks" field that the
listener read back (this relied on JPF restoring static fields when it
backtracks). One bug from that era: an int key was not pooled because
"int" never matched the boxed generic argument in Set<Integer>.

Current fix: plain integer reasoning that the solver handles directly.
  - Every String input is a symbolic integer id plus a null flag
    (x$id, x$nonNull). No String object exists for a symbolic string.
    x == y, x != y and x.equals(y) compare ids, and x != null is the null flag.
    A solved id k is written into the test as the literal "s" + k. The
    concrete string "s<k>" has id k, so a string that is already in a
    collection keeps its id.
  - Membership is expanded over the collection's concrete contents.
    When an assume tests membership of a symbolic key, the collection is fully
    concrete, because every earlier call ran with concrete arguments. The
    collection's code is never run on the symbolic value. Instead, the driver
    loops over the current contents, read through Helper.<name>, with one ==
    per element:
      M.containsKey(k)  -> k == a1 || ... || k == an   (false if empty)
      !M.containsKey(k) -> k != a1 && ... && k != an   (true if empty)
      S.contains(x)     -> the same over the elements
      C[M.get(k)]       -> (k == a1 && C[M[a1]]) || ... over the keys
      Adj.get(a).contains(b) -> the same, over the concrete pairs
    A concrete key is evaluated normally. Any other collection call on a
    symbolic value stops generation with an "unsupported ... in <clause>"
    error.
  - A string operation on a symbolic string (length, charAt, substring,
    startsWith, concat, indexOf, ...) stops generation with
    "unsupported string operation <op> in <clause>; needs a string solver".
Where: symbolic/IntegerModel.java (the clause rewrite, and the runtime
helpers printed into every driver); symbolic/SymbolicDriverPrinter.java;
spf/SpfSymexEngine.java (valueOf turns the solved id and null flag back into a
literal); ir/ParamKind.java (STRING_ID); ir/IrBuilder.java.


10. Keeping TestGen black-box
-----------------------------
Problem: SPF runs the real library, so a symbolic value could leak into it.
That would mean TestGen was reasoning about the library's code rather than
its contract.

Why: SPF executes whatever bytecode the driver calls, and nothing stops a
symbolic value from going in with it.

Fix: Two layers. (a) The driver runs a call only when all of its arguments
are concrete (TestGen.isReady). The program stops at the first call that is
not ready, so symbolic inputs only ever appear in assumes. (b) The
BlackBoxGuard listener checks every method entry into a library class: each
argument, and each field of an object argument. It also checks every field
read executed inside a library class. If any of these values carries a
symbolic attribute, it writes blackbox.txt and stops the search, and the
round fails as BLACK_BOX_VIOLATION. jpf-symbc "*Constant" attributes count as
concrete. verify-generated.sh fails if blackbox.txt is ever non-empty.
Where: symbolic/TestGen.java (isReady, symex); spf/listener/BlackBoxGuard.java;
verify-generated.sh.


11. SPF explores every path
---------------------------
Problem: SPF explores every feasible path. With the pool, StringSet, Graph
and LruCache had 45, 195 and 4374 feasible paths, and the early pipeline
needed a 60-test cap per class.

Why: A depth-first search does not stop at the first answer unless it is told
to.

Fix: The listener calls search.terminate() at the first completed path whose
path condition is solved (genatc.stop_at_first_path, on by default). Each
genCTC round therefore gives one value per input, and each test string gives
one test.
Where: spf/listener/PathVectorListener.java (stateAdvanced).


12. Search time and depth limits
--------------------------------
Problem: A search can run without end, and a depth cutoff must not be
mistaken for "no solution".

Why: Loops in the library, or in the expansion of a large collection, can
make the search very deep or very long.

Fix: run.jpf sets search.depth_limit = 300 and search.time_limit = 60 s
(lowered from 120 s, so that a stuck solve cannot hold a worker for long). It
also bounds symbolic ints to symbolic.min_int = -1000 and
symbolic.max_int = 1000. All of these can be changed with -Dgenatc.spf.*.
The listener records searchConstraintHit events, and a time limit is
reported as TIMEOUT, separately from an incorrect sequence. The external
process kill (section 4) is the last resort.
Where: spf/SpfConfig.java; spf/SpfSymexEngine.java (writeJpfConfig, interpret);
spf/listener/PathVectorListener.java (searchConstraintHit).


13. Locating an impossible test string
--------------------------------------
Problem: When no path completes, we need to know which precondition no path
could get past. The old fix re-ran SPF on shorter and shorter prefixes.

Why: SPF only reports "no path", not why.

Fix: The driver is straight-line code, with one assume per line. The listener
records the highest line of the driver's main() at which a path was pruned
(an ignored state). If a pruned state happens inside a helper method, the
listener uses the main() line that called it. That line is the first assume
no path got past. The engine maps it back to its statement and reports, for
example, "INCORRECT SEQUENCE: call 2 (pop): size > 0". One SPF run is enough.
Where: spf/listener/PathVectorListener.java (instructionExecuted,
searchFinished); symbolic/SymbolicDriverPrinter.java (Printed.at);
spf/SpfSymexEngine.java (interpret); symbolic/TestGen.java (genCTC).


14. Nullable values
-------------------
Problem: Contracts say "x != null", and some values may legitimately be null.
SPF has no symbolic reference that may or may not be null.

Why: Debug.makeSymbolic* only creates numbers and booleans.

Fix: A nullable value is a 0/1 null flag next to its value. In the older
contract-only driver, a string was a pool index plus a flag, and a boxed
number was its value plus a flag, so that results and state (for example,
heap's minValue) could be null. Now a String input is an id plus x$nonNull.
"x != null" becomes the flag. A solved flag of 0 is written as null. A flag
the path condition never mentions means "not null". Boxed number inputs are
still never null: they are created with new Integer(...).
Where: symbolic/IntegerModel.java; symbolic/SymbolicDriverPrinter.java
(symbolicInput); spf/SpfSymexEngine.java (valueOf).


15. Assumes that throw
----------------------
Problem: Evaluating a precondition can throw, for example on a null map entry
or a missing key. An uncaught exception in the driver would look like a
library failure.

Why: The driver is ordinary Java, so an exception in an assume becomes a
property violation in SPF.

Fix: Every assume is wrapped in try { ... } catch (RuntimeException e)
{ ok = false; }, so a throwing assume counts as false and prunes the path.
In the JUnit test, the same exception fails the test.
Where: symbolic/SymbolicDriverPrinter.java (printStatement).


16. Reading SPF's answer, and solver failures
---------------------------------------------
Problem: SPF's console report is meant for people and is hard to parse
reliably. Solver failures (a z3 crash, a missing native library) show up only
as console text.

Why: SPF has no machine-readable output by default.

Fix: The listener solves the path condition itself through jpf-symbc's own
API (PathCondition.solve(), then header.getVarVals) and writes one JSON line
per event: path, error, searchConstraintHit, searchFinished. The generator
reads only that file. Solver failures are recognised from a short list of
console markers ("Error Z3", Z3Exception, UnsatisfiedLinkError, JPFException)
and reported as SOLVER_ERROR.
Where: spf/listener/PathVectorListener.java; spf/PathVectorReader.java;
spf/PathVector.java; spf/SpfSymexEngine.java (solverFailed).


Decisions
=========
These are the decisions taken while removing the pool, without asking:

1. The membership expansion is printed as a loop in the SPF driver over the
   collection's contents, with one == per element. It is not a disjunction
   precomputed in the generator, because the contents exist only inside SPF,
   after the ready calls have run. Each element is one branch, so the path
   condition holds exactly the equalities the disjunction would.
2. "M.get(k) == v" is handled generally. Any clause C that uses M.get(k) with
   a symbolic k becomes (k == a1 && C[M[a1]]) || ... over the keys of M. A
   key that is not in M makes the clause false. This was needed for
   orderservice's "Stock.get(sku) >= quantity". get is expanded only on a
   Map. contains/containsKey are expanded on any collection (Set, Map keys,
   List). Any other call with a symbolic argument is "unsupported".
3. String ids. "s<k>" has id k for |k| < 1,000,000. Any other concrete string
   gets an id below -1,000,000, in the order first seen. That is outside the
   solver's range (-1000..1000), so a solved id can never collide with an
   existing string. The cost is that a symbolic string can never be equal to
   a string the library made itself, unless that string is of the form
   "s<k>". None of the 14 contracts needs that. A solved id may be 0 or
   negative ("s0", "s-1"): lrucache's evictedKey is "s0".
4. Free values are unchanged: 7, 9, 11, ... by input position. A free string
   id gives "s7", "s9", .... A null flag the path condition does not mention
   means "not null".
5. On strings, == and equals are both id equality. The JUnit test keeps the
   contract's ==. That still holds on the correct library, because "s<k>"
   literals are interned and the library stores the same reference.
6. The unsupported-string-operation check covers assumes only, in the round
   where the string is still symbolic. It fires when a string operation is
   applied to a symbolic string input, or takes one as an argument.
   Postconditions are evaluated only concretely, in JUnit, so they may use
   string operations. A string operation on concrete state is evaluated
   normally.
7. "Unsupported" is its own outcome: one new constant each in Solution.Kind
   and TestGen.Result.Status (UNSUPPORTED). The error is raised while the
   round's driver is printed, and SpfSymexEngine turns it into that outcome.
   genATC, genCTC, rewriteATC, symex and isReady are otherwise unchanged.
8. Removed: POOL_SIZE, isPooledType, poolArrayElementType, IrBuilder's
   numeric pool and usedAsKey, ParamSlot's pool/poolReason/membership,
   TestPlan.pooledParams, ParamKind.POOLED (replaced by STRING_ID), the
   driver's pick() and "picks" field, and PathVector.getPicks along with the
   listener code that read it. A unit test fails if "pool", "pick(" or
   "candidates" appears anywhere in src/main/java.
9. The golden files of stack, queue, set, hashmap, bst, graph and lrucache
   were regenerated. The only differences are the chosen input values; this
   was checked by diffing with every literal masked. mathlib, arraylib,
   linkedlist and heap did not change. All 14 libraries generate one test
   each, and every test passes on the correct library. No library's test
   fails.
10. The one-line library descriptions in LibraryRegistry (console output only)
    no longer say "pooled". IMPLEMENTATION_NOTES.md and ARCHITECTURE.md still
    describe the pool, as a record of the earlier designs. They were left
    alone because this task did not ask for them to be edited.
